## 三、測試紀錄

以下區分程式碼檢查與實際測試，尚未親自操作的項目不視為通過。

| 項目 | 實際輸入／操作 | 實際輸出／錯誤 | 人工判讀與修正 | 證據類型 |
|---|---|---|---|---|
| 空白 | 不輸入其他運動偏好，使用下拉選單預設值 | 依照程式設計，空白偏好可以提交，其他欄位仍有預設選項 | 空白偏好不是必填資料，可以正常使用；仍須實際確認 API 回傳 | 程式檢查／未完整實測 |
| 過長 | 在其他運動偏好輸入超過 1000 字的文字 | 程式會顯示「其他偏好文字過長，請縮短至 1000 字以內。」 | 超過限制時停止呼叫 API，避免輸入內容過長 | 程式檢查／未實測 |
| 正常資料 | 選擇運動目標、程度、天數、時間及器材，勾選 API 開關後提交 | 預期產生一週運動計畫，包含摘要、每日項目及一般建議 | 須確認每個欄位是否符合原始輸入，並逐欄檢查運動安排是否合理 | 真實 API／待測 |
| 資訊不足 | 其他偏好留白，或只提供較少的運動需求 | 預期 AI 依照已提供的選項安排，並在資訊不足時提出說明 | 檢查 AI 是否自行假設器材、身體狀況或其他未提供資訊 | 真實 API／待測 |
| 結果保存／再送出失敗 | 先產生一筆計畫，再提交一筆可能失敗的請求 | 程式在每次提交時會先清除舊結果，失敗時顯示錯誤訊息 | 避免失敗後仍顯示上一筆計畫，造成使用者誤認為是最新結果 | 程式檢查／未實測 |
| 缺 key／服務失敗 | 移除 API Key 或模擬 API 連線失敗 | 找不到金鑰時顯示錯誤；其他例外會進入 except 並顯示錯誤類型 | 沒有金鑰時不呼叫 API，服務失敗時不保存結果 | 程式檢查／未完整實測 |
| Cloud 部署（必做） | 使用 Streamlit Community Cloud 部署，輸入一筆正常運動需求 | 尚未完成雲端部署，雲端網址、實際輸出及請求數待填 | 部署完成後須確認老師可以開啟，並檢查雲端 API 是否正常回傳資料 | 未測 |

**6. 本次反思**

這次專題讓我了解如何把 AI API 實際應用在一個可以操作的網頁程式中。原本以為只要輸入問題，AI 就能產生結果，但實際製作後發現，還需要考慮輸入資料、輸出格式、API 金鑰及錯誤處理等問題。

我覺得最有用的功能是每日運動安排，因為使用者可以直接看到每天的運動重點、項目及時間，不需要自己再整理。

製作過程中也遇到虛擬環境、套件安裝及檔案路徑的問題，花了一些時間才成功開啟網頁。目前已經完成本機程式的基本啟動，但雲端部署與真實 API 驗收還需要繼續完成。

目前已知的限制是 AI 產生的運動計畫仍需要人工確認，不能完全取代專業運動指導。下一步希望完成雲端部署，確認 API 可以正常運作，並進一步測試不同使用者需求下產生的運動計畫是否符合預期。
